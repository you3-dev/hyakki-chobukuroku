1. 調査で得た縦画面ゲームUIの定石

縦画面スマホゲームのホーム/ダッシュボード構成のリサーチ要約。詳細は本文の報告を参照。

下部ナビは3〜5項目まで

タブバーは4〜5項目が上限でそれ以上はスケールしない。ゲームでも Home/編成/ショップ等 3〜5個の明快なアイコンが標準形。

NN/g Mobile Navigation Patterns / Appnality
サムゾーン: 操作は下半分へ

片手持ちの親指が届くのは下部中央〜下部側面。主CTAと高頻度ボタンは下半分、タップ領域は44px以上。Marvel Snap開発陣も「操作要素を画面下半分に寄せた」と明言。

Parachute Design Thumb Zone / ArtStation SNAPPY U.I.
和製ソシャゲの標準3分割

上=リソース・プレイヤー情報 / 中央=キャラ・お知らせ / 下=メニュー。「メニューボタンは画面下以外に配置しない」が鉄則とされる。

スマホゲームUI解説記事(neeichi 他)
タブ型 vs ハブ&スポーク型

タブ型は「毎日使う少数タスクが支配的」な場合。ハブ型は「1セッション1目的」の独立機能群向けで、移動が毎回ホーム経由になるコストを払う。

NN/g / Interaction Design Foundation
低頻度項目は「その他」へ退避

設定・引継ぎ等は「その他」タブやシートに格納してよい。ただし「見えない=忘れられる」ので重要機能を入れてはいけない。FGOは設定をマイルーム内へ二段格納。

Appnality / FGO メニュー構成
段階開放(プログレッシブ開示)

機能は必要になった時点で開放する。タスク完了時間20〜40%短縮の報告。Balatroは初期メニュー実質3項目+未解放要素のチラ見せでメタ進行へ牽引。

Celia Hodent GDC講演 / Balatro Wiki
ナビはアイコン+ラベル必須

Marvel Snapのアイコンのみタブは「押すまで何か分からない」とUX批判の定番。文字ラベルを常に添える。

Marvel Snap UI/UX Case Study
周回型の実例: CTA一点集中

FGOは展開式ドック6項目+中央のクエスト群、Marvel Snapは5タブ中央に大Playボタン、Balatroは中央PLAY一択。周回型は「次のラン開始」を最強調するのが共通解。

FGO / Marvel Snap / Balatro 各画面構成

3. 推奨

推奨: 二段階で移行する — まず案2、様子を見て案3(または案1)

① RC期のいま: 案2「出撃ファースト改良ハブ」。現行の4課題(ゼロ実績の一等地占有 / CTA埋没 / 9項目同格 / 重複掲載)をナビ構造を変えずに解消できる。HTML/CSSの組み替えだけで済み、既存のUIガイド規則(共通部品・44px・読み上げ)とも矛盾しない。

② 1.0以降・利用実態が見えたら: 「拠点以外に毎日入る画面が4つ以上あるか」で分岐(NN/g基準)。編成・憑合・図鑑を毎回巡回するプレイが主なら案1(下部タブ)、「開いたら即出撃」が主なら案3(親指ドック)。調査上、周回型デッキ構築の共通解は「次のラン開始を最強調」であり、本作は案3寄りと見る。

③ どの案とも併用可: 段階開放(Balatro/モンスト式)。呪具は所持0の間は非表示、実績・位階は初調伏後に出現、記録(引継ぎ)は設定内へ——とすれば初回の menu は実質4項目まで減り、初見の認知負荷が定石どおり下がる。isNew判定は実装済みなので載せ替えは小さい。

  1. 案2を適用(文言・グリッド構成の変更のみ、ロジック不変)
  2. 段階開放を重ねる(isNew・所持数による表示条件)
  3. 1.0後にプレイ頻度を見て案3/案1を判断(画面シェルの再設計を伴うためマイルストーン扱い)
