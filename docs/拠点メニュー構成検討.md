# 拠点メニュー構成の検討(2026-07-20)

状態: **検討資料(未実装)**。v1.0.0-rc.4 の拠点画面(初回起動時)を対象に、メニュー構成の課題整理と改善案を記録する。採用時は本書の該当案を仕様化し、[UIガイド.md](UIガイド.md) へ規則として移す。

モック: [拠点メニュー構成モック.html](拠点メニュー構成モック.html) をブラウザで開く。現行+3案のスマホフレーム比較で、フレーム内はスクロール可、案1のタブ・その他シートと案3のドックは操作できる。

## 1. 現状の課題

骨格(拠点を起点とするハブ&スポーク)は少画面PWAとして妥当。問題は項目の「数」ではなく「重み付けの欠如」で、次の4点。

1. **ゼロ実績の一等地占有**: 初回起動時、位階/図鑑/夜行/調伏の実績4枠がほぼゼロのまま画面最上部を占める
2. **主CTAの埋没**: 唯一の主行動「最初の夜行へ」がパネル内3段目(目標カード・導入カードの下)にある
3. **9項目が同格**: 毎回使う「編成・憑合」と月1程度の「設定・記録」が同じ2列グリッドに同じ重さで並ぶ
4. **重複掲載**: 図鑑・位階が実績サマリー/目標カード/メニューに重複し、9項目中3つが冗長

## 2. 調査で得た定石(縦画面ゲームUI)

- **下部ナビは4〜5項目が上限**。それ以上はスケールしない(NN/g)
- **サムゾーン**: 片手持ちの親指が届くのは画面下半分。主CTAと高頻度操作は下半分へ、タップ領域は44px以上(Parachute Design、Marvel Snap開発陣も明言)
- **和製ソシャゲの標準3分割**: 上=リソース・プレイヤー情報 / 中央=キャラ・お知らせ / 下=メニュー。「メニューは画面下以外に置かない」が鉄則
- **タブ型 vs ハブ&スポーク型**: タブ型は「毎日使う少数タスクが支配的」な場合。ハブ型は「1セッション1目的」向けで、移動が毎回ホーム経由になるコストを払う(NN/g、IxDF)
- **低頻度項目は「その他」へ退避してよい**。ただし「見えない=忘れられる」ので重要機能は入れない。FGOは設定をマイルーム内へ二段格納
- **段階開放(プログレッシブ開示)**: 機能は必要になった時点で開放。タスク完了時間20〜40%短縮の報告(Celia Hodent GDC講演ほか)。Balatroは初期メニュー実質3項目+未解放要素のチラ見せ
- **ナビはアイコン+ラベル必須**: Marvel Snapのアイコンのみタブは「押すまで何か分からない」とUX批判の定番
- **周回型の共通解は「次のラン開始」の最強調**: FGO=展開ドック+中央クエスト群、Marvel Snap=5タブ中央の大Play、Balatro=中央PLAY一択

## 3. 構成パターン比較

### 案1: 下部タブナビ型

- 構成: 下部固定タブ5つ(拠点/編成/憑合/図鑑/その他)。低頻度6項目(呪具・実績・位階・記録・遊び方・設定)は「その他」ボトムシートへ。ホームは出撃CTA+目標+手持ち妖怪に集中
- 長所: 主要4画面へ常時1タップで拠点経由の往復が消える。親指ゾーンに常設ナビ。画面追加に強い
- 短所: 全画面にナビ常設が必要で**改修規模が最大**(画面シェル再設計)。戦闘中はナビを隠す例外設計が要る。縦の表示領域が約56px減る。運営型ソシャゲの型なので買い切りローグライトでは「ソシャゲ感」が世界観を損ねる恐れ
- 向く状況: 毎日入る画面が4つ以上あるとき(NN/g基準)

### 案2: 出撃ファースト改良ハブ(最小改修)

- 構成: ナビ構造は現行のまま組み替えのみ。CTAをパネル最上段へ、実績4枠→1行チップ、メニュー9項目を「支度3(編成/憑合/呪具・大)+記録3(図鑑/実績/位階・中)+隅3(遊び方/設定/引継ぎ・文字リンク)」に再配分
- 長所: 課題1〜4をすべて解消。頻度=視覚的な重さが一致。**HTML/CSS組み替えだけで実現可能**(ロジック不変)
- 短所: 画面間の往復は引き続き拠点経由。ミニボタン・文字リンクは44px確保に注意
- 向く状況: RC期の低リスク即時改善

### 案3: 親指ドック型(FGO型の縮約)

- 構成: 下部固定ドックに「編成 / 夜行へ(大・中央) / 憑合」、残り7項目は「⋯」からボトムシート。ホーム本文は目標+実績チップ+手持ち妖怪
- 長所: 出撃CTAが常に親指の真下。「編成→出撃」の主要動線が物理的に隣接。調査上、周回型デッキ構築と最も相性が良い型
- 短所: 直接到達は3項目のみで残りはシート内2タップ、発見性が下がる。ドックが拠点専用になりがちで他画面と一貫性が出しにくい。シートの存在を教える導入が必要
- 向く状況: 「開いたら即出撃」が主のプレイ実態

## 4. 推奨

二段階で移行する。

1. **RC期(いま): 案2を適用**。文言・グリッド構成の変更のみでロジック不変。UIガイドの既存規則(共通部品・44px・読み上げ)と矛盾しない
2. **併用: 段階開放**(どの案とも独立に併用可)。呪具は所持0の間は非表示、実績・位階は初調伏後に出現、記録(引継ぎ)は設定内へ。初回のメニューは実質4項目まで減る。実装済みの `isNew` 判定(main.js renderTitle/renderHome)が流用できる
3. **1.0以降: 利用実態で分岐**。「拠点以外に毎日入る画面が4つ以上」なら案1、「開いたら即出撃」が主なら案3。いずれも画面シェルの再設計を伴うためマイルストーン扱いとする
